# 模型接入认证设计（KT 身份直连，零模型 Key 落地）

> 状态：已决策，代码已实现；待跨仓 PR 合入与上线依赖验收。
> 对应能力：ARTEX 的 LLM profile 以 KT 机器身份接入 NewAPI（ktapi.cc），部署内不保存任何模型 API Key。
> 关联：`cloud-end-design`（云端化分层）、new-api `controller/iam.go` / `middleware/auth.go`、
> kt-identity 决策 0023（Casdoor access token introspect）、0008（opaque service principal）。

## 1. 背景

ARTEX 的模型配置原先只有一种形态：管理员把上游 API Key 粘进 `llm_profiles.api_key`（或环境变量）。公司统一 AI 网关 NewAPI（ktapi.cc）上线后有三个选项：

| 方案 | ARTEX 侧保存 | 吊销语义 | 结论 |
|---|---|---|---|
| A. 下发上游 Key | Anthropic/OpenAI 真 Key | 逐处删除，永远删不干净 | 否决 |
| B. 网关 Key（sk-） | 一把部署级 sk- token | 网关侧独立吊销 | 可用，但 sk- 长期落库 |
| **C. KT 身份直连** | **仅身份凭据（client_credentials），零模型 Key** | **吊销身份即断供** | **选定** |

C 与 Kito Harness 桌面端同一条链路：LLM 请求直接携带 KT 身份 Bearer，由 NewAPI 服务端换取 managed relay token，sk- 全程不出服务端。ARTEX 是无人值守服务端 workload，身份用 Casdoor `client_credentials` 机器授权（kt-identity 决策 0023 已打通 introspect）。

## 2. 决策

### 2.1 链路

```text
ARTEX server（VPS / Docker）
  │ ① client_credentials（client_id + client_secret，仅此一份凭据落库）
  ▼
Casdoor token endpoint（https://auth.ktyun.cc/api/login/oauth/access_token）
  │ ② 短时 access token（JWT，exp 建议 1h），仅存内存
  ▼
NewAPI relay（ktapi.cc /v1/chat/completions、/v1/messages…）
    Authorization: Bearer <JWT>
    X-Kito-Token-Name: artex
  │ ③ TokenAuth 中间件：key 非 sk- → introspect（kt-identity）
  │    principalKind=service → 映射机器影子用户 → managed token "artex"
  ▼
上游渠道（真 Key 只在 NewAPI 侧）
```

- ARTEX 只持有**身份凭据**（client_id/client_secret），不是模型 Key：泄漏它无法直接花模型额度，只能换身份 token，且换到的 token 还要过 introspect + 影子用户状态两道闸。
- **权威断供路径**：kt-identity 删除 `client_scope_allowlist` 的 `artex/newapi.relay` 行，或 ktapi.cc 禁用机器影子用户；两者都在 NewAPI 的 introspect 正缓存（当前 60s）内生效。
- **Casdoor 禁用/删除应用只阻止签发新 token**，现有 resolver 不在线检查应用/Token 吊销，已签发 JWT 仍可用至 `exp`。因此它不是即时吊销手段，必须把 `expire_in_hours` 调短（建议 1h），断供操作使用上一条两个入口。
- 日志/UI 全程只见 `client_secret_hint` 尾 4 位，与 `api_key_hint` 同一策略。

### 2.2 契约（消费方义务）

- **introspect 响应**（kt-identity `GET /identity/v1/auth/introspect`，service principal）：
  `active=true, principalKind="service", subject="admin/artex", clientId="artex", audiences, scopes, expiresAt`；**无 accountId/accountNo**。
  new-api 侧需新增 service 分支：合成 `kt_account_id = "svc:" + subject`、用户名取 clientId，复用 `EnsureCommonUser`；managed token 的 `system_managed` provenance 由 NewAPI 持久化。
  **service principal 必须带 `newapi.relay` scope**；仅被 `client_scope_allowlist` 注册不足以花模型额度，避免事件发布等无关机器身份越权进入 relay。
  控制台登录 `/api/iam/ensure` 与长期 sk- 签发 `/api/iam/token/ensure` 仍只接受用户 principal，机器身份一律 403。
- **relay 认证**：`Authorization: Bearer <JWT>` + `X-Kito-Token-Name: artex`（managed 名单新增 `artex`）。service principal 只能使用 `artex`，不能改头冒用 `kito` / `kt-desktop` 等用户产品通道。
  `artex` 的受管身份以持久化 `system_managed` provenance 为准；历史上普通用户自建的同名 token 不被自动升级。
- **token 端点**：标准 OAuth2 `client_credentials`，`expires_in` 驱动缓存刷新。

### 2.3 ARTEX 数据模型

- 新表 `llm_identities`：`name`（唯一）、`token_url`、`client_id`、`client_secret`、`client_secret_hint`、`scope`、`managed_token_name`。多个 profile（旗舰/便宜各档）共用同一身份，凭据不重复存。
- `llm_profiles` 新增：`auth_mode`（`'static'` | `'identity'`，默认 `static`）、`identity_id`（FK → `llm_identities`，`ON DELETE RESTRICT`，删除被引用身份返回 409）。
- 校验：`identity` 模式必须绑定身份且 `api_key` 置空；`static` 模式维持现状（有 key 才可入池）。
- 故障转移池：`PoolProfiles` 的入池条件从「有 api_key」放宽为「有 api_key 或 auth_mode='identity' 且身份有效」。

### 2.4 ARTEX 运行时行为

- **token 生命周期**：懒加载 + 进程内单飞；按 `expires_in` 与 JWT `exp` 取更早者并提前 60s 刷新。绝不延长签发方 TTL，TTL 不超过刷新余量时本次可用但不缓存；token 不落盘、不进日志、不进 llmrec 抓包。
- **401 处理**：relay 返回 401 → `InvalidateIf(失败 token)`（并发下不清掉他人已换的新 token）→ 重放一次；再 401 按硬失败走既有 profile 轮换（llmpool）。
- **重定向**：token 端点与 identity relay 均不跟随重定向，防止 Bearer 跨 origin 或 HTTPS→HTTP 泄漏。
- **兼容**：`static` 模式行为逐字节不变；旧客户端更新已有 identity profile 且未携带 `auth_mode` 时继承库存模式与身份引用；环境变量 bootstrap（`FromEnv`）仍只支持 static，身份模式属于 UI/DB 配置。

## 3. 理由

- **复用而非平行造轮**：NewAPI 本身就是 LLM 数据面的 Broker；身份直连把「谁是调用方」交给 kt-identity，「能花多少」交给 NewAPI 影子用户（分组/额度/计费），不新建任何服务。
- **与 Kito Harness 同构**：桌面端人类用户与 ARTEX 机器身份走同一条 TokenAuth/introspect 代码路径，只多一个 principalKind 分支，维护面最小。
- **吊销即断供**：没有「退出登录删 Key」这个动作——删除 relay scope 或禁用影子用户后，introspect 在既有缓存窗口（当前 ≤60s）内转为拒绝，401。
- **爆炸半径**：ARTEX 被攻破（它本来就是个跑渗透工具的高危 workload）泄漏的是身份凭据与短时 token，不是可直接消费的模型额度；配合 Casdoor 应用 `expire_in_hours` 调短可进一步压缩窗口。

## 4. 非目标

- 不做多租户「每人自带模型」；ARTEX 是单管理员部署。
- 不把 LLM 流量塞进 KTSecret secrets-runtime Broker（那是控制面代执行通道，不适合 SSE 数据面）。
- 不改上游渠道 Key 的管理（仍在 NewAPI 渠道侧/KTSecret）。

## 5. 待定问题

- Casdoor `artex` 应用 `expire_in_hours` 取值（建议 1h；Casdoor 禁用不影响旧 JWT，必须靠短 exp 限制窗口）——上线时定。

## 7. 回滚

- 单 profile 级：`auth_mode` 改回 `static` 并补 `api_key`，立即可用（两列并存，互不破坏）。
- 整体下线：先把 identity profile 切回 `static` 解除引用，再删除 `llm_identities` 与新增列/约束；生产走评审后的前向迁移，不自动执行破坏性 down。

## 8. 约束

- 代码遵循本仓注释风格（中文业务注释）与 new-api 仓 OWASP/测试规范。
- client_secret 与任何 token 不写入日志、llmrec 抓包、issue、对话。
- 兼容 PostgreSQL（本仓仅 PG，schema.sql 幂等 Exec）。
