# 角色化设计（猎杀与收割分流）

> 状态：总纲（skills + agent seed 已落地，触发器/调度接线见 §7）。
> 对应能力：Wave1 四能力（原子操作层、EXP 资产库、CVE 富化工具、价值矩阵调度器）之上的角色编排层。
> （本页按宿主 hook 约定放在 `docs/adr/`——新子系统的架构决策记录。）

## 1. 定位与背景

ARTEX 的 agent 历史上是「通用 worker」：同一个角色既做侦察、又写 EXP、又执行、又写报告。这带来三个问题：

1. **模型错配**：99% 的执行动作是确定性的（发包、判回显），却背着无限制模型的成本；真正需要创造力的 EXP 编写反而和杂活抢同一个上下文。
2. **职责污染**：执行者自我报告「拿下了」直接进 findings，误报无人复核；测绘与利用混在一个会话里，越界动作难以约束。
3. **无法规模化**：串行、贵、依赖模型判断的流程没法横向扩；确定性收割本该高并发跑。

**角色化**把 agent 拆成固定提示词 + 固定工具白名单 + SOP 的窄角色，并按「猎杀 vs 收割」两条流彻底分流：

- **猎杀流（串行、贵、强模型）**：面对没见过的目标/漏洞，由武器匠一次性搞懂它、沉淀参数化 EXP 入库。猎杀是**投资**，允许慢和贵。
- **收割流（并行、便宜、确定性）**：对指纹命中库内 EXP 的目标，收割机批量执行，无 LLM 判断，结论只来自成功判定（oracle）。收割是**红利**，一次猎杀、全平台永久收割。

这与 Wave1 的成功率先验公式一一对应：

```
P(拿下) = P(指纹正确) × P(EXP可用) × P(前置满足) × P(执行无误)
```

- 侦察员修 **P(指纹正确)** 的数据采集（结构化指纹 JSON）；
- 武器匠修 **P(EXP可用)**（EXP 质量 + 靶场验证）；
- CVE 富化修 **P(前置满足)** 的先验（affected 版本区间 + preconditions）；
- 收割机 + 原子操作层修 **P(执行无误)**（确定性执行 + oracle 判定）；
- 价值矩阵调度器决定**今天先打谁**（score = asset_value × P(success) ÷ cost）。

合规语境：这是**授权渗透测试平台**，所有角色所有动作都在书面授权范围内；各 SKILL.md 的「角色纪律」首条都是授权红线。

## 2. 五角色协作图（文字描述）

```
                    ┌─────────────────────────────────────────────┐
                    │  价值矩阵调度器 (valuesched)                  │
                    │  每日对 (资产 × CVE × EXP) 打分取 Top N       │
                    └───────────────┬─────────────────────────────┘
                                    ↓ 派单
   ┌────────────┐   指纹JSON   ┌────────────┐  候选(资产×CVE)  ┌────────────┐
   │ 1 侦察员    │ ───────────→ │ 5 收割机    │ ←────────────── │ 调度器/上游  │
   │ recon-scout│              │ harvester  │                 └────────────┘
   └─────┬──────┘              └─────┬──────┘
         │ insert_assets             │ exp_list_matching 命中 → atomic_* 执行
         ↓                           ↓ attempt(success/failed+归因)
   ┌───────────┐   候选(CVE+指纹)  ┌────────────┐   未命中/批量失败归因
   │ 资产库     │ ───────────────→ │ 2 武器匠    │ ←────────────── 收割机
   │ (assets)  │                  │ weapon-    │
   └───────────┘                  │ smith      │
                                  └─────┬──────┘
        EXP 入库 (ExpLibrary.CreateExpAsset) ↓ → EXP 资产库 (exp_assets)
                                        （收割机下一轮即可命中）
   ┌────────────┐  成功项(目标+EXP+evidence)  ┌────────────┐
   │ 4 记录员    │ ←───────────────────────── │ 3 验证员    │
   │ scribe     │ ←── findings/evidence ────  │ verifier   │
   └─────┬──────┘   list_findings/read_file   └────────────┘
         ↓ 标准化报告（report/ 包格式）
      交付报告 / findings 台账
```

主线（一次完整循环）：

1. **侦察员**对授权目标 `atomic_fingerprint` → 结构化指纹 JSON → `insert_assets` 入资产库；无攻击权限、不验证漏洞。
2. 指纹送两条路：命中已有 EXP 的直接进**收割机**；未命中/需新武器的候选（经调度器排序）进**武器匠**。
3. **武器匠**五步流水线：`vuln_enrich_cve` 富化 → web 搜参考 PoC → 改写参数化 EXP（fingerprint/preconditions/params/exec_template/success_oracle 契约）→ 靶场 `atomic_verify_poc` 正例+负例双验证 → 入 EXP 资产库。
4. **收割机**对命中项按参数模板批量执行，三态判定（命中/未命中/执行失败），成败都记 attempt（失败归因枚举），成功项不自我宣布「拿下」。
5. **验证员**对成功项独立复现一次（不信任收割机自述），三值结论 confirmed / not-reproduced / evidence-insufficient。
6. **记录员**收集全部 evidence，按「时间戳 + 命令 + 回显 + 资产 ID」标准化，confirmed 进正式报告，存疑单列。
7. attempt 台账反哺 EXP 命中率先验 → 调度器下一轮评分 → 闭环。

## 3. 猎杀/收割分流原则

| 原则 | 含义 |
|---|---|
| **决策与执行分离** | 无限制（强）模型只出现在「决策与武器编写」位：选哪个目标（调度器辅助下的人/规划判断）、写什么 EXP（武器匠）。执行走原子操作层，`atomic_*` 是纯 Go 确定性代码，循环里不放 LLM。 |
| **一次猎杀、永久收割** | 任何成功利用必须沉淀为参数化 EXP 才算完成猎杀；没入库的利用是一次性消耗，下次遇到同类目标还要再猎杀一遍——这是反模式。 |
| **执行者不自证** | 收割机的成功报告不算「拿下」，必须经验证员独立复现。防误报是 findings 台账的准入门槛，不是事后补救。 |
| **失败要归因** | 收割失败必须落 attempt + 枚举归因（fingerprint_mismatch / version_mismatch / precondition_missing / timeout / oracle_not_matched / other），这是 EXP 命中率统计与匹配反哺的数据源。归因缺失 = 先验污染。 |
| **角色纪律即越界防线** | 每个角色的工具白名单 + 禁止清单是硬约束（工具层 ToolResolve 按 agent 绑定过滤），提示词里的纪律是软约束的补充；授权边界由任务 scope 与拦截层最终把关。 |
| **便宜角色用便宜模型** | 只有武器匠必须旗舰模型；侦察/收割/验证/记录全可用低成本模型（见 §5）。 |

## 4. 与 Wave1 四能力的对应关系

| Wave1 能力 | 代码位置 | 角色化接点 |
|---|---|---|
| 原子操作层 | `atomic/`（atomic_fingerprint / atomic_weak_cred / atomic_verify_poc），`server/atomic_tools.go` 注入 | 全角色的「手」：侦察员只用 fingerprint；收割机用全部三个；武器匠/验证员用 verify_poc 验证/复核。执行确定性 = 无 LLM 循环。 |
| EXP 资产库 | `db/exp_assets.go`（ExpAsset 契约 + attempt 台账），`server/exp_library.go`（ExpLibrary），`server/exp_tools.go`（exp_list_matching） | 猎杀/收割的**分流枢纽**：武器匠的产出终点、收割机的输入起点；attempt 台账是命中率先验的数据源。 |
| CVE 富化工具 | `server/vuln_enrich.go`（vuln_enrich_cve，多源聚合 + cve_enrich_cache） | 武器匠流水线第 1 步：affected 版本区间 → fingerprint_match，preconditions → EXP 前置条件，P0–P4 → 值不值得打。 |
| 价值矩阵调度器 | `valuesched/`（Candidate/Rank/SelectTopN） | 五角色的**派单层**：score = asset_value × P(success) ÷ cost，P(success) 修正是收割 attempt 统计的反馈目标。 |

## 5. 模型分级建议

| 角色 | 模型档位 | 理由 |
|---|---|---|
| 武器匠 weapon-smith | **旗舰/无限制**（平台最贵档） | EXP 编写是本体系唯一需要创造力与深度推理的环节；串行执行、单位时间吞吐低，贵模型成本可控且收益最大。建议绑定专属 llm_profile。 |
| 侦察员 recon-scout | 便宜档（可用品类里最低） | 动作 = 调一次指纹工具 + 归纳字段，几乎无判断量。 |
| 收割机 harvester | 便宜档，且**执行路径无模型参与** | 执行与判定全在原子操作层；模型只做参数准备与异常上报，甚至可被编排器直调原子操作替代（见 §7 远期）。 |
| 验证员 verifier | 便宜档 | 复现是确定性的；模型只做证据齐全性核对与三值结论映射。 |
| 记录员 scribe | 便宜偏中（要写通顺中文报告） | 整理格式化为主；如对报告文采有要求可单独升档，但不影响安全性。 |

落库方式：agents 表 `llm_profile_id` 按 agent 绑定（优先级：agent 绑定 → 任务/会话 pin → 全局 active）。seed 只建 agent 不绑 profile，由管理员按上表在 LLM 管理页绑定。

## 7. 接线计划（遗留）

1. **EXP 入库 API**：武器匠第 5 步当前走服务层 `ExpLibrary.CreateExpAsset`，尚无 agent 工具/HTTP API（`server/exp_library.go` 只有 service 层）。计划：`POST /api/exps` 管理接口 + （或）`exp_submit` agent 工具（绑武器匠），入库即触发收割机对已积累指纹的重扫。
2. **角色触发器**：reporter 已示范 OnToolCall 触发（report_finding → 报告撰写）。同模式可接：侦察员 `insert_assets`(service) → 收割机指纹队列；收割机成功项 → 验证员；验证员 confirmed → 记录员。harvester 的 parallel + none 触发策略已随 seed 落好，只差 CreateTrigger 接线。
3. **收割机去模型化（远期）**：attempt 记录工具化（`record_attempt` 绑收割机）后，收割主循环可由编排器直接串原子操作完成，模型只兜异常上报——成本进一步趋零。
4. **侦察员/验证员/记录员 agent seed**：等触发器接线一起做（单独 seed 无触发链路意义有限；当前可先在任务里以 skill 形式由 worker 按白名单代跑）。
5. **调度闭环**：valuesched 的 P(success) 因子接 exp_attempts 实测命中率（ExpStats），替代静态先验；每日 Top N 直接生成收割机任务单。
